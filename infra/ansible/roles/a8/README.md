# role: a8

**Що робить:** описує кодом машину A8 — середовище, у якому агент працює в контейнері, і демон черги (`a8-tick`, §7), що бере задачі. **Таймер демона постачається вимкненим.** До цієї ролі машина була налаштована руками, тобто існувала лише на диску; після неї стан відтворюється з чистого клону за одну команду.

**Чого роль НЕ робить** — і це не борг, а межа:

## 1. Застосування

```bash
cd infra/ansible
cp inventory.a8.ini.example inventory.a8.ini   # вписати адресу і користувача з sudo

ansible-playbook a8.yml --syntax-check                       # без машини взагалі
ansible-lint a8.yml roles/a8/                                # без машини взагалі
ansible-playbook a8.yml -i inventory.a8.ini --check --diff    # сухий прогін
ansible-playbook a8.yml -i inventory.a8.ini                   # застосувати
ansible-playbook a8.yml -i inventory.a8.ini --tags verify     # ДОВЕСТИ результат
```

Останній рядок — не формальність. Він єдиний відповідає на питання «спрацювало чи ні».

**Окремий playbook, а не роль у `site.yml`** — три причини в шапці [`a8.yml`](../../a8.yml). Коротко: інша група хостів, інший набір ролей, і небажання тягнути в A8-прогін vault із prod-секретами, які цьому play'ю не потрібні.

## 3. Запобіжники: як ними користуватись

```bash
a8-guard check                 # ПЕРЕД задачею; 0 — можна, 10/11/12 — ні
a8-guard check-run             # ПЕРЕД стартом контейнера; лише kill switch
a8-guard count                 # після того, як задачу взято
a8-guard record ok|failed      # після завершення
a8-journal append <task> <source> <result> <sec> <model> [нотатка] [ключ=значення ...]
a8-journal reject <task> <поле:причина,...>
a8-journal event <стан> <пояснення>
```

Коди виходу `a8-guard`: **10** — kill switch на місці, **11** — денний ліміт вичерпано, **12** — три падіння поспіль.

**Чому дієслів два.** `check` відповідає на питання «чи можна БРАТИ НОВУ ЗАДАЧУ» і його ставить демон рівно один раз на задачу. `check-run` відповідає на питання «чи можна ВЗАГАЛІ щось виконувати» і його ставить обгортка `a8-run-agent` перед кожним стартом контейнера — а їх на одну задачу кілька: залежності, перевірка хука, агент, оракул приймання. Денний ліміт і пауза після трьох падінь — політика набору роботи; запуск контейнера задачею не є. Kill switch перевіряється обома: він мусить зупиняти геть усе.

Злиті в одне дієслово, ці питання давали конкретну ваду: лічильник задач інкрементується вже після запуску агента, тож на останній дозволеній задачі дня обгортка відмовляла б кодом 11 усім наступним викликам — зокрема прогону оракула, — і демон записував би це як червоний оракул. Агент зробив би роботу правильно, а машина відхилила б її за вичерпаний ліміт.

**«Падінь поспіль» рахується з кінця журналу до першого не-`failed`**, а не як «скільки `failed` серед останніх трьох». Зупинка в обох редакціях настає в один і той самий момент, але звіт відрізнявся: на стані `failed failed ok` вікно друкувало 2, тоді як падінь поспіль нуль — успіх скинув лічильник.

**Kill switch — це просто файл:**

```bash
touch /home/agent/STOP      # зупинити чергу
rm /home/agent/STOP         # відпустити
```

`a8-journal` відмовляє (`exit 2`), якщо поле `source` не одне з `human|external|derived`. Це **fail closed** з OQ-34: відсутність поля має бути помилкою, а не мовчазним дефолтом «можна все» — саме так контроль не зникає при рефакторі.

## 4. Контейнер: чому саме такі прапорці

Усі вимоги зібрані в одному місці — `/usr/local/bin/a8-run-agent`. Кожен рядок має коментар із протоколом виміру. Два, які легко зняти, не зрозумівши наслідку:

- **`-t` відсутній.** Це не недогляд форматування. З псевдотерміналом `git push` без креденшала **зависає** (`Username for 'https://github.com':`, потім `exit 124`); без нього падає одразу (`128`). Для непильнованого демона зависання гірше за падіння: класифікатор виходу побачить таймаут і віднесе його не туди.
- **`PATH` починається з `node_modules/.bin`.** Без цього `.git/hooks/pre-commit` виконується, не знаходить `lefthook`, друкує попередження — і коміт **проходить**. Тобто ні ESLint, ні `tsc`, ні `prettier`, ні `ruff` у контейнері не працюють, а виглядає це як робочий захист.

## 4-bis. Група `docker`: що ця межа тримає і чого не тримає

**Факт** (вимір №7): `agent` справді без sudo (`sudo: a password is required`), але `getent group docker` → `docker:x:988:runner,agent`. Членство в `docker` дорівнює root на хості: `docker run -v /:/host …` від імені `agent` дає повний доступ до хоста.

**Тримає:** агент **усередині контейнера** (UID 1002, зняті підтвердження) до docker не дістається — `a8-run-agent` не монтує `/var/run/docker.sock`, і V6 перевіряє це в живому контейнері. Шлях «модель у контейнері → root на хості» через docker закритий.

**Не тримає:** будь-який процес, що працює як `agent` **на хості**, — майбутній демон, cron, людина в `sudo -u agent`, — фактично root. Передумова ADR-039 §2 «користувач без sudo» формально виконана, а по суті — ні.

**Чому роль це не «лагодить»:** без групи демон не запускав би контейнери взагалі. Rootless docker або вилучення з групи міняють контракт ADR-039 §2 — питання класу A для yurii, винесене в опитування PR. Компенсація, яку призначає `docs/19` §B.1, — **жодних prod-креденшалів на машині** (§7 п.1): ставши root, агент не дістане нічого від prod.

## 5. Що `--tags verify` доводить і чого НЕ доводить

**Доводить:** стан (теки, файли, групи, конфіги) і поведінкові твердження — V5 (guard справді відмовляє на всіх трьох запобіжниках), V6 (UID, `$HOME`, відсутність TTY у реальному контейнері), V7 (git не падає на `dubious ownership`, identity саме задана), V8c (журнал пише 6 полів і відкидає невідомий `source`), V10 (`lefthook` досяжний), V12 (заборонені шляхи справді ro), V13 (пін Python доходить до контейнера).

**НЕ доводить:**

1. **Що демон коректно бере задачу і віддає результат.** Демон є (§7) і доведений у CI на заглушці контейнера (`tools/scripts/a8-tick.test.sh`), але **жодного разу не виконував справжньої задачі на A8**. Зелений `verify` — про середовище, не про поведінку системи.
2. **Що `pre-commit` блокує поганий коміт.** V10 доводить, що `lefthook` **досяжний**. Довести блокування можна лише мутацією репо (спробувати закомітити свідомо невалідний файл і чекати ненульового коду) — це рівень демона, не `verify.yml`, який не має права псувати робоче дерево.
3. **Що egress-allowlist фільтрує.** За дефолту примус вимкнено (§6). V9 доводить, що набір наповнюється і таймер живий, — не те, що зайве відрізається.
4. **Що `push` працює.** Роль креденшала не створює; без нього `push` падає на автентифікації (вимір №7).
5. **Що конфігурація переживе перехід репо в private.** Зараз репо публічне, тому `fetch`/`ls-remote` працюють без креденшала. Після private read-шлях теж його потребуватиме.
6. **Що `uv sync` проходить.** V13 доводить, що пін `UV_PYTHON=3.12` доходить до контейнера. Сам `uv` роль в образ не ставить — повний `uv sync` лишається перевіркою рівня демона.
7. **Що ro-список достатній для довільної сесії.** М-3-fix перевірив чотири інструменти (`touch`, `pnpm`, `uv`, `vitest`); агент може викликати інше (Playwright, `drizzle-kit`, генератори). V12 доводить, що п'ять шляхів ro, — не те, що нічого іншого не зламається.
8. **Що стан таймера правильний у `--check`.** У сухому прогоні юніт-файл фізично не пишеться, тож задача `Enable egress refresh timer` пропускається (`not ansible_check_mode`). Її доводить V9 після справжнього застосування.

## 6. Egress-allowlist: увімкнення примусу

Дефолт — `a8_egress_enabled: true`, `a8_egress_enforce: **false**`. Тобто набір адрес наповнюється і його видно, але `DROP` усього іншого не застосовано. Так зроблено навмисно: увімкнути мережевий фільтр наосліп означає ризикнути тим, що демон **тихо** втратить мережу, а в журналі це виглядатиме як зависла задача.

Порядок увімкнення — по одному кроку, з перевіркою між ними:

```bash
# 1. Наповнити набір і подивитись, що в ньому
sudo systemctl start a8-egress-refresh.service
sudo ipset list a8_egress | head -30

# 2. Подивитись поточний ланцюг ДО змін (позиції мають значення)
sudo a8-egress-rules status

# 3. Застосувати правила
sudo a8-egress-rules apply

# 4. Перевірити, що контейнер ще має мережу
sudo -u agent a8-run-agent /home/agent/hart bash -c 'git ls-remote origin | head -3'

# 5. Якщо щось не так — зняти одним рядком
sudo a8-egress-rules remove
```

**Правила примусу не постійні — і роль це компенсує лише частково.** Вони вставляються `iptables -I` і зникають після ребуту, після `ufw reload` (який перечитує `DOCKER-USER` з `/etc/ufw/after.rules`) і після рестарту docker — на A8 стоїть ручний drop-in `docker.service.d/ufw-reload.conf`, що робить `ufw reload` після кожного старту docker. Для ребуту це факт; для `ufw reload` — **висновок, не вимір**: блок `# BEGIN A8 DOCKER-USER` в `after.rules` оголошує ланцюг рядком `:DOCKER-USER - [0:0]` (прочитано read-only 2026-09-18), а таке оголошення в `iptables-restore` очищує ланцюг; перевірити на A8 означало б зробити запис. Звідси два рубежі. **Перший — drop-in** `docker.service.d/zz-a8-egress.conf` (лише коли примус увімкнено): `ExecStartPost=-/usr/local/bin/a8-egress-refresh` після кожного старту docker, тобто й після ребуту. Ім'я «zz-» — частина механізму: `ExecStartPost` із різних drop-in'ів виконуються в порядку імен файлів, тож наш іде **після** ручного `ufw-reload.conf`, який інакше стер би щойно повернуті правила. «-» перед командою означає, що збій оновлення не зупинить docker. **Другий рубіж — таймер** `a8-egress-refresh`: повертає правила не пізніше ніж за 30 хв після `ufw reload`, зробленого руками. Вікно після старту docker тепер — час між стартом docker і завершенням `a8-egress-refresh`, а не 30 хв. **НЕ ПЕРЕВІРЕНО на A8:** що drop-in справді закриває вікно, доведе лише рестарт docker з увімкненим примусом (запис на A8, крок yurii).

**Позиція правил обчислюється, а не пишеться числом.** У `DOCKER-USER` першим стоїть stateful-`RETURN` (`RELATED,ESTABLISHED`); вставка **перед** ним обрізала б зворотний трафік усіх контейнерів, і це виглядало б як «мережа зникла». Вставка **після** фінального `RETURN` не досягалася б узагалі. Скрипт шукає останній стейтовий `RETURN` і вставляє одразу за ним.

**Чого цей механізм не дає — і це властивість, не баг.** Allowlist осмислений у **доменах**, `iptables` оперує **адресами**:

1. CDN-адреса, видана між оновленнями таймера, ще не в наборі — запит обірветься;
2. два домени на одному CDN-IP не розрізняються: дозволивши один, ви дозволили обидва;
3. резолв робить скрипт, а не контейнер, тож вони можуть отримати різні адреси того самого імені.

Це **межа наслідку**, а не доменний фільтр. Справжній доменний фільтр потребує HTTPS-проксі — інша конструкція контейнера (винесено в опитування PR).

**DNS дозволено окремо і першим.** Без цього не працює нічого: контейнер спершу резолвить ім'я, і якщо DNS-сервер не в наборі, жоден дозволений домен недосяжний за визначенням.

**Який саме DNS — виміряно, не припущено.** На A8 `/etc/resolv.conf` містить лише стаб `127.0.0.53`; контейнеру docker підставляє upstream із `/run/systemd/resolve/resolv.conf` (`192.168.1.1`). Перша версія скрипта читала лише перший файл — із примусом резолв у контейнері зник би повністю. Тепер читаються обидва, а V9 перевіряє, що кожен IPv4-upstream у наборі. IPv6-upstream (`fdc6:…::1`) у набір не йде: набір IPv4, і `ip6tables` роль не чіпає — тобто IPv6-егрес контейнерів **не фільтрується взагалі**, навіть із примусом.

## 7. Демон черги `a8-tick`

**Форма — разовий скрипт під таймером, не довгоживучий процес.** Один тік бере щонайбільше одну задачу, виконує, пише журнал і завершується. ADR-039 §3 вимагає, щоб стан жив у git і черзі на диску, ніколи в пам'яті. Процес, що помирає після кожної задачі, порушити це не може за побудовою. Таймер **вимкнений** (`a8_tick_timer_enabled: false`). Вмикається зміною змінної, а не `systemctl enable`: інакше наступне застосування ролі поверне стан назад.

**Стан задачі — це тека, де лежить її файл:** `agent-queue/` (чекає) → `running/` (узята) → `done/` · `failed/` · `rejected/`. Задачу, зупинену запобіжником або 401, повертають у чергу: її не виконали.

### Запис черги

```json
{
  "id": "fix-footer-42",
  "source": "human",
  "origin": "feedback",
  "oracle": "pnpm --filter @flatcraft/web test -- footer",
  "prompt": "Опис задачі…",
  "model": "sonnet"
}
```

| Поле     | Значення                                                       | Відмова, якщо                                                                                         |
| -------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `id`     | `[A-Za-z0-9._-]`, ≤64 символи; іде в гілку `ai/<id>`           | немає → `id:missing`; інший алфавіт → `id:invalid`                                                    |
| `source` | довіра до тексту (OQ-34): `human`, `external`, `derived`       | немає → `source:missing`; інше → `source:invalid`; відоме, але ще не дозволене → `source:not-allowed` |
| `origin` | джерело (`CLAUDE.md` §0): `direction`, `analytics`, `feedback` | немає → `origin:missing`; інше → `origin:invalid`                                                     |
| `oracle` | тест/скрипт, що доводить результат                             | немає або порожній → `oracle:missing`                                                                 |
| `prompt` | текст задачі — **дані** в промпті супервізора (OQ-34 п.3)      | немає → `prompt:missing`                                                                              |
| `model`  | необов'язкове; дефолт `a8_default_model`                       | —                                                                                                     |

**Режим (а) OQ-34:** доки звужені набори дозволів для `external`/`derived` не реалізовані й не покриті тестом, приймається лише `human` (`a8_sources_allowed`). Запис відмови в журналі перелічує **кожне** поле, що не пройшло: `{"event":"reject","fields":["source:missing","oracle:missing"]}`.

### Тік і що буває, якщо він помре саме тут

| #   | Крок                                          | Якщо процес убито тут                | Що зробить наступний тік                                                                              |
| --- | --------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 0   | Сироти з `running/`                           | запис `failed` може задвоїтись       | ще раз `failed orphan`, перенесе у `failed/` — песимістично, безпечно                                 |
| 1   | `a8-guard check`                              | нічого не змінено                    | те саме заново                                                                                        |
| 2   | вибір задачі, `mv` у `running/`               | задача в `running/`, роботи не було  | `failed orphan` — **песимістично**: задача не починалась, але зарахується як падіння                  |
| 3   | `fetch` + worktree від `origin/main`          | гілка `ai/<id>` і worktree лишаються | `failed orphan`; повторна задача з тим самим `id` отримає `failed: гілка вже існує` — не перезапис    |
| 4   | `pnpm install`, `uv sync`, `check-hook-loud`  | те саме                              | те саме                                                                                               |
| 5   | агент (`a8-run-agent` → `claude -p`)          | **контейнер живе далі**              | `docker kill a8-<id>` (ім'я детерміноване), потім `failed orphan`                                     |
| —   | `a8-guard count`                              | лічильник міг не збільшитись         | сирота рахується тут, тож ліміт не обходиться                                                         |
| 6   | класифікація; при 401 — запис kill switch     | kill switch міг не записатись        | `failed orphan`; причина 401 у журналі губиться, але наступна задача знову впаде на 401 і запише STOP |
| 6b  | оракул приймання (`a8-run-agent` → `bash -c`) | **контейнер живе далі**              | `docker kill a8-<id>-oracle`, потім `failed orphan` — результат не доставлено, бо push іде після      |
| 7   | `push`                                        | push міг пройти                      | `failed orphan`, хоча результат доставлено — **хибно-песимістично**; видно по гілці на GitHub         |

Тут чотири свідомі рішення порядку.

- **Оракул — ДО push'а, не після.** Сенс кроку в тому, щоб неперевірений результат не виходив назовні. Червоний оракул лишає гілку і worktree на місці: вони доказ для людини, а не сміття.
- **`a8-guard count` — після запуску агента, не до.** Причиною було те, що `a8-run-agent` викликав `a8-guard check`. З розділенням дієслів (обгортка кличе `check-run`) причина зникла, і лічильник можна перенести до запуску — це закрило б вікно, у якому вбитий посеред задачі тік лишає задачу непорахованою. Зміна стосується обліку, а не оракула, і чекає на власний крок; чинний порядок тримає мутація в `a8-tick.test.sh`.
- **При таймауті демон вбиває контейнер.** `timeout` вбиває лише клієнт `docker run`, а контейнер з агентом працював би далі без нагляду.
- **Невідомий клас виходу — `failed`.** Порожній `cls` (класифікатор упав) спершу проходив повз `case` на push як успіх. Знайшло рев'ю agy №1, закрито гілкою `*)`.

### Класифікатор (ADR-039 §4)

`401 Invalid bearer token` **разом з ознакою помилки** (`rc ≠ 0` або `"is_error": true`) означає `auth_stop`: демон пише kill switch із причиною і повертає задачу в чергу. Той самий рядок в успішному прогоні (агент читав ADR-039) — не зупинка. Класу «quota» **немає**: сигнатуру ще не бачили. Усе невідоме — `failed`. Коди 10/11/12 від обгортки означають, що спрацював запобіжник, а не агент упав (`stopped`).

### Push

`a8_push_credential_kind: none` (дефолт) — задача закінчується станом `no-credential`, **не** `ok`. `deploy_key` → `git push` по SSH з `~/.ssh/id_push`; `token_file` → `GIT_ASKPASS=/usr/local/bin/a8-git-askpass` читає `/etc/a8/push-token` у момент запиту. Обидва шляхи **НЕ ПЕРЕВІРЕНІ**: креденшала не існує. Гілка — завжди `ai/<id>`, force-push немає, PR демон не створює.

### Чого демон не робить

Не мержить. Не створює PR (це роль воркфлоу, якого ще немає). Не змінює лейбли, не чіпає `main`.

Оракул задачі демон **проганяє** — у тому самому контейнері й тому самому worktree, де працював агент, і **до** push'а. Код виходу пишеться в журнал полем `oracle_rc`: `0` — прийнято машиною, ненульове — `failed oracle` без push'а, `-` — до оракула не дійшло (задача впала раніше). Поле `oracle` цитує намір, `oracle_rc` каже, чи намір доведено; без другого перше не відрізняє прийняту роботу від неперевіреної.

Це не робить CI зайвим: оракул доводить конкретну задачу на машині, CI — що результат не зламав решту після push'а.
