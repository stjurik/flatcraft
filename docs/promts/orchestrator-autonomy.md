# Оркестратор на T470: коли вирішує сам, коли радиться з agy, коли питає yurii

> **Для сесії-оркестратора на T470.** Читається разом із
> `docs/promts/orchestrator-handoff-2026-09-23.md`. **Працюй за CLAUDE.md §0.**
>
> Навіщо цей документ: yurii сказав, що не розуміє, про що його питають. Причина не в
> ньому. Питання, яке інженер-конструктор мусить «перекладати», — погане питання. А
> більшість питань не треба ставити взагалі.

## 1. Хто вирішує

| Що вирішується                                                                                                                  | Хто                                                                                                                                                                                    | Як                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Технічна дрібниця з очевидним дефолтом, оборотна                                                                                | **сам**                                                                                                                                                                                | вирішив і записав одним рядком у розділ PR «Рішення без питання»            |
| **Будь-яке інше технічне питання** — розвилка, «як краще», «чи правильно я розумію»                                             | **сам + agy** (§3), **не yurii**                                                                                                                                                       | обираєш ★ сам; якщо agy не погоджується, обидві позиції йдуть у PR дослівно |
| Незгода тебе й agy, що стосується **продукту або незворотного**                                                                 | **yurii**                                                                                                                                                                              | питання за §2, обидві позиції — у ньому, простими словами                   |
| Незгода тебе й agy в усьому іншому                                                                                              | **сам**                                                                                                                                                                                | обираєш ★; обидві позиції — у PR дослівно, yurii не питаєш                  |
| Рецензія власного PR                                                                                                            | **не ти**: основний шлях — agy, дві моделі (§3.1); окрема сесія Claude (напр. хмарна `flatcraft-8b`) теж допустима, зокрема для архітектурних і безпекових PR, — тоді це пишеться в PR | автор не перевіряє сам себе (§0 п.2); модель для рецензії — §3              |
| Продукт: що бачить користувач (вигляд, поля, поведінка, тексти)                                                                 | **yurii**                                                                                                                                                                              | питання за §2                                                               |
| **Клас A:** креденшали й доступи, merge, налаштування GitHub чи акаунтів, видалення, гроші, будь-що незворотне, зміна контракту | **yurii, лише його словами в цій сесії**                                                                                                                                               | питання за §2, **без дефолту**, чекати                                      |

**До yurii йдеш лише з трьома речами:** продукт, клас A, незгода з agy щодо продукту чи
незворотного. Технічне питання, поставлене yurii, — це питання, яке ти мав поставити agy
(рішення yurii 2026-09-23).

**Дрібниця — це не питання, а рішення.** Перший рядок таблиці не виняток із правила
«технічне — спершу agy»: там немає питання, лише очевидний дефолт, записаний одним рядком.
Критерій — чи зміг би ти назвати другий розумний варіант. Зміг — це вже розвилка, і вона
йде до agy. Сумніваєшся, чи дрібниця, — теж до agy.

**agy ніколи не дає згоди**, лише технічну думку. Думка agy — гіпотеза, тож перед тим, як
на неї спиратися, звір її з кодом (§0 п.3). У журналі agy є виклики з вигаданими фактами.

## 2. Як питати yurii

yurii оцінює **результат**, а не реалізацію. Питання описує **наслідок** кожного варіанта
для продукту, машини або його самого. Механізм у питання не потрапляє.

```
ПИТАННЯ [клас A | продукт]
Що вирішуємо: <одне речення без термінів>
Чому зараз: <що стоїть, поки немає відповіді>
1 ★ <варіант>: <що зміниться для вас / продукту / машини>. Відкотити: <так, як | ні>.
2   <варіант>: <наслідок>. Відкотити: <…>.
Якщо промовчите: <клас A — «нічого не роблю, чекаю»; продукт — що зроблю>.
Відповідь: «1» або «2».
Технічно (для довідки): <команди, файли, ідентифікатори — одним рядком, в кінці>
```

**Правила:**

- не більше трьох варіантів;
- одне питання в одному повідомленні;
- не більше 3 питань на задачу і 10 на добу (§0 п.4); перевищив — зупинись зі звітом
  «потрібне уточнення постановки»;
- терміни (`worktree`, `scope`, `oracle`, `rebase`, SHA) — **лише** в рядку «Технічно».

**Самоперевірка перед відправкою:** чи зрозуміє це людина, яка не знає слів із рядка
«Технічно»? Якщо ні, ти ще сам не зрозумів наслідків. Спершу розберись або спитай agy.

**Приклад — те саме питання, поставлене погано і добре** (справжній випадок 2026-09-22):

> ❌ «Пуш зонда відбито: токену `gh` бракує scope `workflow`. Як діємо? (1) refresh зі scope
> (2) без зонда (3) пушиш сам (4) змінити спосіб перевірки»

> ✅ ПИТАННЯ [клас A]
> Що вирішуємо: чи дати мені на хвилину дозвіл змінити налаштування автоматичних перевірок на GitHub.
> Чому зараз: без цього нову функцію «PR створюється сам» не перевірити наживо.
> 1 ★ Дати на хвилину: я роблю один запис, ви одразу забираєте дозвіл (дам три команди). Відкотити: так, забрати дозвіл.
> 2 Не давати: функція піде в роботу неперевіреною. Відкотити: так, перевірити пізніше.
> Якщо промовчите: нічого не роблю, чекаю — це зміна вашого доступу.
> Відповідь: «1» або «2».
> Технічно: `gh auth refresh -s workflow` → push → `gh auth refresh -r workflow`.

## 3. Як радитись з agy

> **Правило yurii від 2026-09-23.** Будь-яке технічне питання — спершу до agy, не до yurii.
> agy працює на **власній квоті** і дає доступ до кількох моделей; кожній роботі — своя.

**Коли:** будь-яке технічне питання (§1); незалежна рецензія власного PR; пошук
контрприкладів до свого рішення; звірка фактів; розбір логів. **Не для** згоди і не для
питань продукту.

> Claude — той самий, на якому працюєш ти.

**Вибір моделі — лише прапорцем, і лише з доказом.** Без `--model` agy бере модель за
замовчуванням, і тоді невідомо, чию статистику рахувати. Тому виклик завжди такий:

```bash
agy -p "<промпт>" --model <id з таблиці> --log-file /tmp/agy-<тема>.log
```

Прапорці стоять **після** промпту — так виклик проходить за дозволом профілю `agy -p *`
без натискання (перевірено зондом 2026-09-23: agy їх розбирає). Лог — поза репозиторієм.
Після виклику модель підтверджує рядок логу:

```bash
grep -o 'Propagating selected model override to backend: label="[^"]*"' /tmp/agy-<тема>.log
```

Ранні рядки логу «not in local config → resolved via default» — шум до входу в акаунт, на
них не зважай. Якщо рядка `Propagating …` немає, модель **не підтверджена**: в
`agy-stats.md` пишеш `невідомо → <модель за замовчуванням у момент виклику>` (поле `model` у
`~/.gemini/antigravity-cli/settings.json`). Як такий запис рахується — §3.4.

### 3.2. Межі: agy — лише думка

- **Без bash.** У кожному промпті — явна заборона запускати команди.
- **Запис — лише в `docs/promts/inputs/`.** Межі перевіряєш після **кожного** виклику.
- **Жодних дій, що потребують натискання yurii, через agy.** Якщо дія потребує його
  кліку, вона потребує його рішення, і обхід через іншу модель цю вимогу не знімає.
- **Ніколи `--dangerously-skip-permissions`** і ніколи інтерактивний режим.

### 3.3. Процедура виклику

Правила з `docs/promts/ai-review-local.md` чинні дослівно; нижче — з урахуванням моделей.

1. Перед викликом: `git status --porcelain > /tmp/agy-baseline.txt`.
2. Контекст — **файлом** `docs/promts/inputs/_agy-<тема>.md`: `agy -p` не читає stdin, тож
   попроси прочитати файл через `read_file`. Передавай шляхи, а не вміст коду. **Лише
   абсолютні шляхи** — і до файла контексту, і до файлів у ньому: відносний шлях agy шукає у
   власній теці `~/.gemini/antigravity-cli/`, а не в репо. Так 2026-09-23 два виклики або не
   знайшли файл, або знайшли його обшуком диска субагентом, тобто командами, які правило
   забороняє.
3. У промпті — **явна заборона bash** (інакше agy мовчки завершиться без результату).
4. Виклик — як у §3.1, з `--model` і `--log-file`.
5. Після виклику: `git status --porcelain | tools/scripts/check-agy-scope.sh /tmp/agy-baseline.txt`.
   Запис поза `docs/promts/inputs/**` означає STOP, відкат роби лише руками yurii.
6. Модель — з логу (§3.1), не з пам'яті.
7. Кожне твердження agy звір із кодом і познач: ✅ перевірено / ❌ вигадано / НЕ ПЕРЕВІРЕНО.
8. **Кожен виклик — рядок у `docs/promts/inputs/agy-stats.md`**, з міткою моделі з логу.
   Незалогований виклик робить поріг недійсним (§0 п.2). В останню колонку, «Справжніх
   знахідок», — скільки тверджень пройшли п.7 **і привели до правки** коду, тесту чи
   документа; правдиве зауваження без правки знахідкою не є.
9. Видали транзитні файли `_agy-*` і лог.

У PR вердикт agy йде **дослівно**, з твоїми позначками з п.7 і назвою моделі. Для ризикового
PR це **два** вердикти — основний (Gemini 3.8 Flash, не-Claude) і контрприклади (Opus або
окрема сесія Claude Code, §3.1); для звичайного — один, основний. Якщо рецензенти
розійшлись між собою або з тобою, у PR видні **всі** позиції дослівно (§0 п.2): розбіжність
моделей цінніша за їхню згоду.

**Текст правил дорівнює рішенню yurii — не вужчий і не ширший.** Урок yurii 2026-09-24
дослівно: «не вносити в контракт звуження вашого рішення, а показувати обидві позиції».
«Не ширший» стоїть на тому самому: дописати наслідок, умову чи виняток, яких yurii не
називав, — теж змінити контракт без його згоди, а це `CLAUDE.md` §0 п.4 і так відносить до
питань yurii. Правило однакове для всього тексту правил — `CLAUDE.md`, ADR, цей документ — і
для будь-якого джерела зміни:

- **зауваження рецензента** правдиве, але внести його можна лише змінивши рішення yurii;
- **власне доповнення**, яке здається очевидним.

В обох випадках слова yurii лишаються як були, а в PR поруч стоять обидві позиції. Якщо
вважаєш, що **рішення yurii** варто змінити, — це вже питання класу A (§1): за §2, без
дефолту, чекати. PR із двома позиціями такого питання не замінює. Перевірка перед кожною
правкою тексту правил: вона змінює **те, що** вирішив yurii, чи лише **як** це записано?
Змінює — текст не чіпай. Лише формулювання (вирішене лишається тим самим) — звичайна робота,
не клас A.

_Два випадки 2026-09-24, обидва в #137:_

- **Звуження.** Gemini 3.8 Flash помітив, що «`agy` або свіжа Claude-сесія» дає змогу обійти
  двох рецензентів. Оркестратор вписав у правку «свіжа Claude-сесія — лише коли `agy`
  недоступний». yurii відхилив це: «звужує контракт понад моє рішення».
- **Розширення.** yurii поширив іспит на кожну модель, а оркестратор приписав кожній і
  наслідок «у Розвідника», який правило 2026-09-15 називало лише для Gemini. Помилку знайшов
  Gemini 3.8 Flash.

Це клас «текст правил не збігається з рішенням yurii», два повтори за день. Третій повтор за
правилом трьох (`CLAUDE.md` §0 п.6) означає задачу «змінити процес».

### 3.4. Поріг довіри — для кожної моделі окремо

Рахує `bash tools/scripts/agy-stats-summary.sh`, руками число не переписується. **Кожна
модель складає свій іспит** (рішення yurii 2026-09-24): вікно — її виклики від 2026-09-15,
крім позначених дослівною фразою `**У вікно OQ-35 не зараховано**` (виклик без тверджень).
До 10 викликів у вікні — «рано судити»; на 10+ частка викликів із ≥1 вигадкою **не нижче
50%** означає, що ця модель іде з ролі Рев'юера (CLAUDE.md §0 п.2). Куди саме — правило
2026-09-15 задало лише для Gemini 3.1 Pro: у Розвідника (`docs/20` OQ-35); для інших моделей
це рішення yurii. Інші моделі провал однієї не зачіпає. Колонка «Знахідок» у виводі — скільки справжніх знахідок
дала модель у вікні: вигадки кажуть, наскільки їй не можна вірити, знахідки — що вона дала.

**Сумнів рахується проти моделі** (рішення yurii 2026-09-23). Виклик із непідтвердженою
моделлю **і вигадками** йде в рахунок моделі, що стояла за замовчуванням у момент виклику.
**Чистий** непідтверджений виклик не зараховується нікому. Невідомий виклик із вигадками без
названої моделі за замовчуванням скрипт рахувати відмовляється — це дірка в даних, її
закривають у журналі.

## 4. Робочий цикл

1. Бери наступну нитку з пакета передачі §2 або ту, яку назвав yurii.
2. Окремий worktree від свіжого `origin/main`, одна гілка — один автор.
3. Робота → тести → друга думка agy, якщо була розвилка → **draft** PR із розділами «Як
   перевірити очима» і «Рішення без питання».
4. Рецензія не автором.
5. Коротке повідомлення yurii (§5). Далі переходь до наступної **незалежної** нитки, не
   чекаючи merge. Якщо нитка залежить від попередньої, чекай.

**Перед кожною публікацією** текст іде у файл і публікується через
`tools/scripts/check-leak.sh <файл> && gh …`. Публікація — це заголовок і опис PR,
коментар, issue, дослівний вердикт рецензента, повідомлення коміту. Механічно цього ніщо
не вмикає: рядкове правило, як і решта в §6, — не межа.

- **Вихід 1** — у тексті адреса або рядок із файла відомої адреси. Прибери адресу або заміни
  документаційною.
- **Вихід 3** — файла відомої адреси немає, він не читається або порожній: «не перевірено»,
  а не «чисто». Свідомо без правила 1 — лише `LEAK_ORIGIN_FILE=none`, видно в команді.
- Якщо адреса мусить лишитися в тексті (дослівний вердикт рецензента) — STOP. Публікація
  незворотна, тож це питання класу A за §2.

Документаційні діапазони RFC 5737 і RFC 3849 — лише попередження. До 2026-09-30 перевірка
жила поза git, завжди виходила з 0 і тому нічого не зупиняла (коментар до #159, PR #170).

**STOP і звіт:**

- CI червоний і не лагодиться за дві спроби;
- потрібна дія, яку забороняє профіль, — навіть якщо інша форма команди її пропустила б (§6,
  «Заборонене — STOP і питання»);
- `check-leak.sh` блокує текст, який мусить піти як є;
- постало питання класу A;
- вичерпано бюджет питань;
- суперечність із CLAUDE.md;
- щось із нотатки пріоритету 0 довелося б писати в git.

### 5.1. Щоденні числа — у кінці роботи

Рішення yurii 2026-09-23. Одне число на рядок, без пояснень; пояснення — лише якщо число
незвичне.

```
ЧИСЛА ЗА <дата>
Питань yurii:          <N>
Натискань yurii:       <N>
agy, викликів / вигадок:
  Gemini 3.1 Pro:      <N> / <N>
  Claude Opus 4.6:     <N> / <N>
  Gemini 3.8 Flash:    <N> / <N>
  Claude Sonnet 4.6:   <N> / <N>
  невідомо:            <N> / <N>
```

- **Питань yurii** — питання за §2 (продукт, клас A, незгода з agy). Прохання «зробіть дію»
  з рядка «ЧЕКАЄ ВАС» — не питання, їх рахуєш окремо, якщо yurii попросить.
- **Натискань** — скільки разів сесія чекала підтвердження yurii. Прямо оркестратор цього
  не бачить: погоджений виклик виглядає так само, як дозволений профілем. Тому число дає
  лічильник — хук на подію `PermissionRequest`, який спрацьовує рівно на кожен показаний
  yurii діалог (профіль оркестратора, `tools/scripts/log-permission-request.sh`):
  `bash ~/.flatcraft/hooks/log-permission-request.sh --count <РРРР-ММ-ДД>`. Якщо
  `install-orchestrator-profile.sh --check` не каже `OK`, лічильник не встановлено або його
  копія розійшлась із `main` — тоді число «НЕ ПЕРЕВІРЕНО», а не оцінка.
- **agy** — з `agy-stats.md` за день, модель — з мітки логу (§3.1). Вигадки — з колонки
  «Вигаданих фактів», після верифікації (§3.3 п.7).

## 6. Дозволи

Кожна команда в терміналі без дозволу чекає натискання yurii (25.09 — 128 натискань за
день, лічильник #134). Прибирають їх **не ширшим allow, а режимом Auto** — це рішення після
рецензії PR #141 (Gemini 3.8 Flash, Claude Opus 4.6, звірка оркестратора з документацією
Claude Code):

- у режимі Auto дію, якої немає в allow, перевіряє модель-вартовий замість кліку;
- дія, що **збігається з allow, вартовому не показується взагалі**. Тож широке правило
  (`git *`, `tools/scripts/*`, `sort *`, `ssh … *`) не економить кліків, а вимикає перевірку:
  `git -c alias.x='!…' x` під `Bash(git *)` пройшов би повз вартового;
- deny і ask діють у будь-якому режимі.

Звідси профіль `.claude/settings.orchestrator.json` (ставить
`tools/scripts/install-orchestrator-profile.sh`, CI перевіряє профіль і інсталятор на кожному PR):

- **allow — вузький**: конкретні підкоманди git і gh, тести й перевірки, `*.test.sh`, agy,
  `verify` ролі A8. Інсталятор відмовляє на правилі, що дає довільну дію: `git *` і `git -c`,
  `tools/scripts/*`, `uv run … *` (крім pytest/ruff/mypy), `pnpm run/exec/dlx`,
  `pnpm --filter *`, `npx` (крім `prettier --check`), утиліти, що читають чи пишуть будь-який
  файл (`sort`, `jq`, `cut`…), інтерпретатори і **будь-який `ssh`** — `ssh a8-ro -o
ProxyCommand=…` виконує команду локально ще до з'єднання.
  Тека `~/hart-wt` — робоча (`additionalDirectories`): читання у worktree-ах не питає.
- **ask** — питає навіть у режимі Auto: два інсталятори запобіжників, `autorun.sh`, два
  скрипти `measure-*`, довіра agy до теки, зонд agy, `gh workflow run`. Названо поіменно:
  шаблон `install-*` чіпляв би й їхні `*.test.sh`, і кожен прогін тесту питав би yurii.
- **deny** — «ніколи» в будь-якому режимі, для форм, які Claude пише найчастіше: force-push
  (зокрема `+гілка`), push у `main` (зокрема `git push -u origin main`), видалення гілок на
  origin (`--delete`, `:гілка`), `git reset --hard`, `git clean`, **встановлення** мітки
  `ai-approved` (точка контролю yurii, `docs/17`; читати issue з нею можна), схвалення власних
  PR, merge, `gh auth`, `gh secret`, `sudo`, docker, живий Discord (кореневий
  `discord:apply` і `apply` пакета будь-якою формою `pnpm`), нові залежності, правки
  CLAUDE.md, ADR, контракту шаблонів, `.github/`, міграцій, снапшотів, bend-матриці, читання
  `~/.ssh`, `~/.flatcraft`, `~/.config/gh`, vault-пароля.

**Перевірено на справжньому Claude Code, а не лише тестом.** Тест звіряє профіль із 43
зразками команд емуляцією правил — у CI справжнього Claude Code немає, а емуляція — лише
прочитання документації. Правило вже раз не діяло, як написано: кінцеве `:*` Claude Code читає
як стару форму «префікс і будь-які аргументи», тож `Bash(git push * :*)` не забороняв
`git push origin :гілка` — цього не побачили ні автор, ні обидві рецензії (правильно — `:**`;
інсталятор тепер відмовляє на такій пастці). Тому після кожної зміни профілю чи оновлення
Claude Code — `CLAUDE_BIN=<бінарник сесії> bash tools/scripts/probe-profile-rules.sh`: ті самі
зразки, справжній механізм дозволів, заглушки замість git/gh/pnpm. Для allow, ask і «немає
правила» проба робить контрольний прогін, тож доводить саме правило профілю, а не збіг.

**Версія важить.** До 2.1.282 правило з `*` одразу після двокрапки не діє жодною формою
(виміряно 2026-09-28 на `echo` з контролем: 2.1.280 і 2.1.281 — ні, 2.1.282 і 2.1.283 — так).
Проба 2026-09-28: на 2.1.283 — 43 з 43; на 2.1.280 — 42 з 43, `git push -u origin :feat/x`
виконується. На T470 сесія оркестратора у VS Code — 2.1.282 (заборона діє), а CLI у терміналі,
через який ідуть headless-прогони, — 2.1.280 (не діє): `claude update`. `--check` попереджає,
якщо CLI старіший за 2.1.282. На попередньому профілі (`ca89e26`) `git push -u origin main`
і `:feat/x` виконувались (виміряно на 2.1.283).

**Чесно про межі.** Рядкові правила — не межа: документація Claude Code сама пише, що
`Bash(git push *)` не зупиняє `git -C . push origin main`. Так само текстом не закрити
`git push -u origin HEAD`, коли дерево стоїть на `main`: у команді немає слова `main`. Правила ловлять те, що Claude пише
зазвичай; жорстку межу, яку не обходить форма виклику, дає лише пісочниця Claude Code
(sandboxing). Її вмикання — рішення yurii, клас A.

**Заборонене — STOP і питання, а не інша форма (рішення yurii 2026-09-30).** Якщо deny
профілю зупиняє потрібну дію, той самий результат не добувається іншою формою команди:

- правка файла — ні інтерпретатором, ні `sed`/`tee`;
- docker — ні через `ssh`, ні через `ansible`;
- push — ні іншим написанням.

Згода yurii на **зміст** правки — не згода на **шлях**. Це STOP за CLAUDE.md §0 п.7 і §4:
пункт зупиняється, незалежні нитки тривають (§4 п.5). У звіті — питання класу A за §2 з
варіантами:

- а) yurii робить дію сам — дай точну команду чи текст;
- б) разова іменна згода саме на цей шлях;
- в) механізм у git, що не потребує обходу (перевірка у `verify.yml`, мітка yurii тощо).

Два випадки класу «заборону обходить інша форма команди»:

- #151 — force-push в автономному профілі;
- #167 — `CLAUDE.md` у #158 правили інтерпретатором, бо `Edit(CLAUDE.md)` заборонено.

Третій випадок за правилом трьох (CLAUDE.md §0 п.6) — задача «змінити процес».

**Прибирання.** Кожне «Так, більше не питати» дописує в локальний файл одноразовий дозвіл.
`install-orchestrator-profile.sh --check` показує, скільки їх накопичилось і чи є серед них
небезпечні. `--replace` скидає до профілю все, що **дає** права (allow, робочі теки, хуки), а
все, що **обмежує** (власні deny і ask yurii), лишає. Резервна копія — поза репо. Потрібну
команду, якої бракує, додає PR у профіль — точною формою, без `*` після імені програми.
Правило з `*` інсталятор приймає лише дослівно з переліку перевірених форм (`WILDCARD_OK` в
`install-orchestrator-profile.sh`): шаблон небезпечних форм ніколи не буде повним, тож нова
широка форма — окремий, помітний рядок у PR, а не один із десятків у профілі.

Кожна з цих гарантій тримається тестом, і це перевірено мутаціями: сценарій 28
`install-orchestrator-profile.test.sh` ламає інсталятор по одному місцю і вимагає, щоб набір
упав на кожному мутанті; CI ганяє це на кожному PR.

`ssh` на A8 без кліку зараз не дозволяє жодна форма — інсталятор відмовляє на будь-якому
`ssh`, навіть точному. Виняток для однієї точної команди без `*` (наприклад, фіксованого
виклику звіту) додається окремим PR — і лише після того, як на A8 стоятиме ключ `a8-ro` з
`a8-ro-shell`. Це новий ключ, тобто клас A — рішення yurii.

## 7. Вхідні yurii — hart-inbox

> **Рішення yurii 2026-10-04 (клас A).** Вхідні yurii — приватний репозиторій
> `stjurik/hart-inbox`. Дві форми, зручні з телефона: «Зауваження до сайту» й «Ідея
> виробу». Їхнє джерело, як і мітки, — `tools/inbox/` у git flatcraft; у hart-inbox їх
> переносить `tools/scripts/inbox-setup.sh`.

**Мітки:** `нове` → `оброблено` → `в беклозі` / `потрібна відповідь` / `відхилено`. Мітку
типу (`зауваження`, `ідея`) ставить сама форма.

**Коли:** раз на день або на команду yurii «розбери вхідні».

**Порядок:**

1. **Забрати.** У `~/hart` на свіжому `main` виконай `bash tools/scripts/inbox-pull.sh`.
   Писати agy може лише в `docs/promts/inputs/` головного дерева, а не worktree. Скрипт
   кладе кожне нерозібране issue в `docs/promts/inputs/_inbox/<N>/`: текст, зображення й
   назви відкритих issues flatcraft. Тека `_inbox/` — у `.gitignore`. Деінде скрипт писати
   відмовляється.
2. **Чернетка agy.** Для кожного `<N>` викликай agy за `docs/promts/agy-inbox.md` (Gemini 3.8
   Flash), з процедурою §3.3 і рядком у `agy-stats.md`. Вихід — `_inbox/<N>/draft.md`.
3. **Твоя перевірка.** Звір кожне `[репо: …]` з кодом і позначай за §3.3 п.7. Перевір, чи
   справді оракул-кандидат почервоніє.
4. **Зауваження → issue в беклозі flatcraft.** Лише текст, без чужих фото. Скріни даються
   посиланням на приватний запис hart-inbox. Публікуй через
   `tools/scripts/check-leak.sh <файл> && gh issue create … --body-file <файл>` (§4).
5. **Ідея → специфікація draft PR-ом** у `docs/promts/inputs/new-part-<slug>.md`. У роботу —
   лише після «так» yurii.
6. **Відповідь у hart-inbox** — лише мітка й коментар:
   `bash tools/scripts/inbox-pull.sh mark <N> <в беклозі|потрібна відповідь|відхилено> <файл>`.
   У коментарі — посилання на issue чи PR або причина.
7. **Питання — yurii одним списком**, у звіті.

`inbox-pull.sh` бере на розбір лише issues без мітки `оброблено`. Issue знову потрапляє на розбір,
коли мітку `оброблено` знято.

символ у символ.
