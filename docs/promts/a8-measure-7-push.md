# Вимір №7 — `push` із контейнера, останній невідомий у git-шарі

> **Що це.** Вимір №6 (PR #111) закрив `status`, `worktree add` і `commit` у контейнері й
> свідомо **не** чіпав `push`: він потребує креденшала і вихідної мережі — два додаткові
> невідомі, які зіпсували б читання решти. Тепер вони міряються окремо, і саме вони лишились
> між нами й Стадією 1: демон, який не вміє віддати результат, не демон.
>
> **Роль:** Розвідник (`docs/15` §0). **Модель:** сильна (Opus) — класифікація падінь тут
> тонка, три різні причини дають схожий на вигляд вивід.
> **Гілка:** нова від свіжого `origin/main`.
> **Працюй за CLAUDE.md §0.**
>
> **Цей прогін нічого не створює в акаунті.** Ні PAT, ні deploy key, ні секрета, ні
> branch-protection. Він міряє те, що вже є, і готує yurii рішення. Деталі — §6.

## 1. Вхідні умови — з виміру №6, не переміряй

Контейнер піднімай **у конфігурації, яку вимір №6 визнав придатною**, інакше ти міряєш не
`push`, а знову те саме:

1. `--user 1002:1002` — UID контейнера = власник примонтованого репо. Не root: root лишає в
   репо файли, яких `agent` не видалить (15 штук у §3.2 протоколу).
2. `$HOME` існує і **записуваний** (`-e HOME=…` на створену й `chown`-нуту теку). Для самих
   git-операцій не обов'язковий, для `pnpm` — обов'язковий.
3. **git-identity задається явно** — репо-локально або `GIT_AUTHOR_*`/`GIT_COMMITTER_*`. Це
   єдина умова, яку правильний UID не знімає: без неї `commit` → 128
   `unable to auto-detect email address`.

Дослівний `docker run` цього прогону **зберігай у звіті** (`docs/16` §8.2 п.5). Відсутність
такої команди від М-3 коштувала окремого прогону на з'ясування, що саме мірялось.

## 2. Інвентаризація — спочатку подивись, що взагалі є

Перед будь-яким `push` з'ясуй **дослівно**, який креденшал у контейнері вже присутній. Не
припускай ні наявності, ні відсутності: обидва варіанти вже траплялись і обидва давали схожий
вивід.

```bash
git -C /repo remote -v
git -C /repo config --get remote.origin.url
ls -la "$HOME/.ssh" 2>&1
ls -la "$HOME/.git-credentials" 2>&1
git -C /repo config --get-all credential.helper 2>&1; echo "exit=$?"
env | grep -iE '^(GH_TOKEN|GITHUB_TOKEN|GIT_ASKPASS|SSH_AUTH_SOCK)=' | sed 's/=.*/=<є, значення не друкуємо>/'
```

⚠️ **Останній рядок навмисно не друкує значень.** Токен у звіті = токен у публічному
репозиторії. Друкуй лише **факт наявності** змінної.

**Важливий фон, який змінює читання.** Репозиторій зараз **публічний** (ADR-038 прийнято,
виконання відкладено — OQ-30). Тому `fetch`/`ls-remote` по HTTPS працюють **без жодного
креденшала**, а `push` — ні. Це подарунок для виміру: read-шлях і write-шлях розділяються
самі собою, без додаткової роботи. І це ж — **межа виміру**: коли репо стане private, результат
розділу A треба переміряти. Запиши це у «чого прогін НЕ доводить».

## 3. Розвилка класу A — який креденшал дати демону

Це **питання до yurii, не до тебе** (`CLAUDE.md` §0 п.4, клас A: незворотне — створення
креденшала в чужому акаунті). Твоє завдання — **подати таблицю з наслідками**, підперту
дослівними виводами §2 і §4, і зупинитись. Дефолту при мовчанні тут немає.

| #   | Варіант                                                                  | Плюс                                                                    | Мінус                                                                                                                    | Наслідок для Стадії 1                                                        |
| --- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| а   | SSH deploy key з правом запису, змонтований у контейнер `ro`             | Не залежить від акаунта yurii; відкликається одним кліком; не має TTL   | Deploy key не звужується до гілок — ключ із write пише в `main` так само легко, як у гілку задачі                        | Демон може запушити куди завгодно; захист доведеться будувати на боці GitHub |
| б   | Fine-grained PAT, `contents: write` на один репозиторій, через env       | Найтонше з трьох по правах; має термін дії; видно в аудиті акаунта      | Живе **в акаунті yurii** — витік = дії від його імені; термін дії треба поновлювати руками (черга yurii росте)           | Найменша поверхня, найбільше ручної роботи                                   |
| в   | ★ Deploy key + воркфлоу, що сам відкриває draft PR на push у гілку `ai/` | Демон **фізично не має** прав на PR і merge — лише запис у свій простір | Треба написати воркфлоу — а `.github/**` заборонений шлях (`CLAUDE.md` §6), тобто це окрема іменна згода, як для PR #114 | Демон віддає роботу, але не може її прийняти. Рівно та межа, яку ми й хотіли |

**Чому ★ саме (в).** Варіанти (а) і (б) відповідають на питання «чим підписати push», але
лишають відкритим «що станеться далі»: хтось має перетворити гілку на PR, і зараз цей хтось —
yurii, руками, на кожну задачу. (в) відповідає на обидва питання одразу і при цьому **звужує**
права, а не розширює: демон пише у власний простір імен і не має інструмента створити PR,
поставити лейбл чи змержити. Ціна — один воркфлоу, який попросить окремої згоди.

**Не обирай сам і не готуй креденшал «щоб було».** Таблиця + дослівні факти — деліверабл.

## 4. Чотири прогони. Третій — головний, і він має **впасти**

Порядок не довільний: кожен наступний читається лише тоді, коли попередній дав відповідь.
Виконуй усі чотири **в одному й тому самому контейнері** (§1).

### A — мережа без креденшала. Контроль усього виміру

```bash
timeout 60 git -C /repo ls-remote origin 2>&1 | tail -5
echo "exit=${PIPESTATUS[0]}"
```

**Очікування, записане ДО:** exit 0, список ref'ів. Репо публічне — читання не потребує
підпису.

Це **контроль**, без якого решта не читається (`docs/16` §8.2 п.1). Якщо A зелений, а B
червоний — причина в креденшалі. Якщо A **теж** червоний — причина в мережі, і про креденшал
цей прогін не сказав нічого; так і пиши, не підставляй висновок.

### B — `push` у власну гілку. Пара з контролем на зависання

Спершу зроби порожній коміт у worktree (як у вимірі №6), тоді:

```bash
# B1 — так, як зробить демон: без інтерактиву
timeout 90 env GIT_TERMINAL_PROMPT=0 \
  git -C /tmp/wt-push push origin HEAD:refs/heads/probe/push-7 2>&1 | tail -10
echo "exit=${PIPESTATUS[0]}"

# B2 — контроль: те саме БЕЗ GIT_TERMINAL_PROMPT
timeout 90 git -C /tmp/wt-push push origin HEAD:refs/heads/probe/push-7 2>&1 | tail -10
echo "exit=${PIPESTATUS[0]}"
```

**Навіщо пара.** Для непильнованого демона **зависання гірше за падіння**: процес, що чекає на
`Username for 'https://github.com':`, не дасть ні помилки, ні результату — задача просто не
закінчиться, а класифікатор виходу (ADR-039 §4) побачить таймаут і віднесе його не туди. B1/B2
відрізняються **однією** змінною (`docs/16` §8.2 п.4) і показують, чи потрібен
`GIT_TERMINAL_PROMPT=0` у конфігурації демона як обов'язковий, а не як гігієна. `exit 124`
хоч в одному з них — це окремий рядок у вимогах до образу.

**Очікування, записане ДО:** якщо §2 не знайшла креденшала — обидва падають; B1 швидко і з
явним `could not read Username` / `Authentication failed`, B2 повисне до `timeout`. Пріор
слабкий: я не знаю, що саме лежить у `$HOME` контейнера — позначаю це наперед (`docs/16`
§8.2 п.2).

### C — `push` у `main`. Це і є головне питання прогону

```bash
timeout 90 env GIT_TERMINAL_PROMPT=0 \
  git -C /tmp/wt-push push --dry-run origin HEAD:main 2>&1 | tail -10
echo "exit=${PIPESTATUS[0]}"
```

**Очікуваний і бажаний результат — ВІДМОВА.** Це не перевірка «чи вміємо ми пушити в main» —
це перевірка, **чи існує хоч що-небудь, що демону цього не дасть**. Сьогодні на це немає
жодної механічної лінії: `deny`-списки покривають `git push --force`, але не звичайний
`push origin HEAD:main`; `check-forbidden-paths.sh` дивиться на **шляхи у diff'і**, а не на
цільовий ref.

Тому читання таке:

| Спостереження                             | Вердикт                                                                                |
| ----------------------------------------- | -------------------------------------------------------------------------------------- |
| Відмова через відсутній креденшал         | ⚠️ «захист» тримається лише на тому, що ключа нема. Після §3 він зникне                |
| Відмова через protected branch            | ✅ лінія існує на боці GitHub — назви її дослівно                                      |
| `--dry-run` повертає 0 (тобто прийняв би) | ❌ **знахідка прогону:** нічого не тримає. Branch protection стає передумовою Стадії 1 |

⚠️ **`--dry-run` прибирати заборонено.** Ні за яких результатів, ні «щоб перевірити напевно».
Прогін, який поклав probe-коміт у `main`, знецінює сам себе і порушує §6.

⚠️ **Межа читання, яку назви у звіті чесно:** `--dry-run` домовляється із сервером, але не
всі серверні відмови гарантовано відтворюються на dry-run так само, як на справжньому push.
Тому «`--dry-run` дав 0» слід читати як «механічної лінії **не видно**», а не як «справжній
push точно пройшов би». Різницю закриває незалежна перевірка, read-only:

```bash
gh api repos/stjurik/flatcraft/branches/main/protection 2>&1 | head -20; echo "exit=$?"
```

(404 = захисту немає; 200 = є, і тоді дивись, які саме правила.) Виконуй її **з хоста**, не з
контейнера — вона не про контейнер.

### D — форма, у якій працює демон: `fetch` → `rebase` → `push` із worktree

Вимір №6 залишив `fetch` і `rebase` поза прогоном явним рядком (§6 п.3). Демон робить їх на
кожній задачі, і робить **із worktree**, а не з кореня клону — а конфіг remote живе у
спільному `.git`, не у worktree.

```bash
timeout 90 git -C /tmp/wt-push fetch origin main 2>&1 | tail -5; echo "exit=${PIPESTATUS[0]}"
timeout 90 git -C /tmp/wt-push rebase origin/main 2>&1 | tail -5; echo "exit=${PIPESTATUS[0]}"
```

Плюс окремо: чи спрацьовує хук при **справжньому** коміті (вимір №6 бачив лише
`lefthook install`, і §6 п.6 прямо це виділив). Досить одного дослівного рядка: `pre-commit`
знайшов `lefthook` у `PATH` чи ні.

### Прибрати за собою

`/tmp/wt-push`, локальні гілки `probe/*`, і — якщо B **пройшов** — віддалену гілку
`probe/push-7`. Перевір дослівно: `git ls-remote --heads origin 'probe/*'` → порожньо.

## 5. Не змішуй мережу з креденшалом

Контейнер Стадії 1 матиме **allowlist вихідної мережі** (`docs/19` §6). Якщо він уже
застосований у твоєму прогоні — скажи це **до** виводів, і тоді прогін A перестає бути просто
контролем і стає ще й перевіркою самого allowlist'а. Якщо не застосований — теж скажи: інакше
наступний читач вирішить, що `push` міряли крізь фільтр, якого не було.

Три причини падіння дають схожий на вигляд вивід, і сплутати їх легко:

- **мережа** — `Could not resolve host`, `Connection timed out`, `Failed to connect`;
- **креденшал** — `Authentication failed`, `could not read Username`, `Permission denied (publickey)`;
- **права на ref** — `protected branch hook declined`, `refusing to allow …`.

Класифікуй **лише за дослівно побаченим рядком**. Сигнатура, якої ти не бачив, у звіт не
потрапляє (`CLAUDE.md` §0 п.3; це та сама дисципліна, що й для класифікатора виходу
ADR-039 §4).

## 6. Чого не робити

- **Не створюй PAT, deploy key чи будь-який інший креденшал** — ні в акаунті yurii, ні в
  репозиторії, ні «тимчасово для виміру». Це незворотна дія в чужому акаунті і рівно та
  розвилка, яку §3 виносить на yurii.
- **Не вмикай branch protection.** Навіть якщо прогін C покаже, що її нема, — це рекомендація
  у звіті, не дія.
- **Не прибирай `--dry-run`** з прогону C і не пуш нічого в `main`.
- **Не друкуй значення токенів і ключів** — лише факт наявності.
- Не пиши воркфлоу з варіанта (в): `.github/**` — заборонений шлях, і згоди на нього в цьому
  прогоні нема.
- Не чіпай `CLAUDE.md`, `docs/03_DECISIONS.md`, `infra/**`, `packages/db/src/migrations/**`,
  `packages/db/src/schema.ts`, `workers/cad/tests/snapshots/**`,
  `docs/12_TEMPLATE_CONTRACT.md`, `packages/cad-engine/data/bend-machine-esi.yaml`.
- Не займайся D.1 (private) і D.2 (self-hosted runner) — рішення yurii 2026-09-16.
- Не пиши демон, systemd-юніт і проєктний Dockerfile. Разовий контейнер — інструмент виміру.
- `agy` цьому прогону не потрібен. Якщо все-таки викличеш — залогуй у
  `docs/promts/inputs/agy-stats.md`; вікно OQ-35 зараз читається **2 з 10**, незалогований
  виклик робить поріг недійсним (`CLAUDE.md` §0 п.2).

## 7. STOP-тригери

Зупинись зі звітом, якщо:

- у виводі зустрілось `401 Invalid bearer token` — потрібен інтерактивний логін, автоматика
  далі неможлива (`CLAUDE.md` §0 п.7);
- існує файл `/home/agent/STOP`;
- контейнер не піднімається у конфігурації §1 — тоді ти міряєш не те, що вимір №6 визнав
  придатним;
- `--dry-run` у прогоні C повернув 0 **і** з'явилась спокуса перевірити «справжнім» push'ем:
  це саме той момент, заради якого написаний §6;
- для будь-якого кроку потрібен креденшал, якого нема, — це **результат**, а не перешкода.
  Запиши і йди далі.

**Окремо** (`docs/16` §8.2 п.6): якщо якийсь STOP-тригер перекриває саме те, що прогін
посланий виміряти, — це дефект цього промпту. Скажи прямо у звіті, не обходь мовчки.

## 8. Форма звіту — у draft PR

1. **Інвентаризація §2** — дослівно, без значень токенів.
2. **Таблиця по чотирьох прогонах:** очікування ДО / факт / контроль був? / вердикт. Кожен
   рядок — з дослівного виводу, не з міркування.
3. **Дослівні виводи** всіх команд, з `${PIPESTATUS[0]}`, і **дослівна команда `docker run`**,
   якою створено середовище.
4. **Вердикт по `push`:** чи може демон Стадії 1 віддати результат. Так / ні / так за умови X.
5. **Вердикт по `main`:** що саме — дослівно — не дає туди запушити, і чи існує ця лінія
   взагалі. Разом із виводом `gh api …/protection`.
6. **Таблиця §3** з твоїми доповненнями, які випливли з фактів.
7. **Вимоги до образу Стадії 1** — доповнення до трьох із виміру №6, **сформульовані після
   прогону**, кожна з дослівного рядка.
8. **Як перевірити очима** — 5–10 тверджень: команда або файл, без читання коду.
9. **Чого цей прогін НЕ доводить** — окремим списком. Публічність репо туди входить
   обов'язково.
10. **Опитування** — §3 як мінімум, шість полів на кожне питання (`CLAUDE.md` §0 п.4).

Повний протокол — новим файлом `docs/promts/inputs/measurement-7-push.md` (конвенція
`measurement-6-git-in-container.md`). Готовий рядок для таблиці вимірів `docs/20` — окремим
блоком у звіті: `docs/20_OPEN_DECISIONS.md` живе лише в гілці
