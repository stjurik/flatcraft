### C.3. Merge-base guard

`docs/16_AUTONOMOUS_RUNS.md:83-92` документує явний скрипт-патерн (`git fetch origin main`, `test "$(git merge-base HEAD origin/main)" = "$(git rev-parse origin/main)"` → STOP при розбіжності) для **вже існуючої** гілки, що продовжує роботу.

`ai-fix.yml:34-38` реалізує **сильніший** механізм для того самого класу ризику іншим способом: замість перевірки-і-стопу, крок `git fetch origin main && git checkout -b fix/issue-N origin/main` СТВОРЮЄ нову гілку прямо від `origin/main` — розбіжність структурно неможлива (немає старої гілки, яку продовжують). Не ідентичний код, той самий інваріант, сильніше гарантований для одноразового CI-запуску (не підходить для «continue» сценарію, де скрипт `docs/16` і потрібен).

### C.4. Terminal-state guard

`.github/workflows/ai-triage.yml:105-121` — крок «Verify issue reached a terminal state (ADR-035 §2)»: перевіряє, що issue має РІВНО один із трьох термінальних лейблів (`ai-plan-ready`/`ai-architectural`/`ai-need-info`) після прогону, інакше `exit 1`. Задокументовано в коментарі коду як реакція на конкретний інцидент (issue #84, прогін `30616535686`, 2026-07-31 — job був зеленим, а issue завис без стану). **Працює, підтверджено кодом і його власною історією.**

Це узгоджується з явним рішенням T1 п.2 (`docs/02_ROADMAP.md:32-37`) — «лишається ручним ритуалом», не є прихованим розривом, ОКРІМ digest-cron, який задекларований як завершений («✅»), а не як «ручний за вибором».

## G. Вартість CI

**Метод:** 3 останні змерджені PR (`gh pr list --state merged --limit 3`), для кожного — CI-прогін на його гілці (`gh run list --branch <branch>`), job-тайминги (`gh run view --json jobs`), сума тривалості кожного job'а (billed = ceil до хвилини на кожен job, стандартна модель GitHub Actions billing для Linux-раннерів, множник ×1).

| PR                                    | Гілка                     | CI run ID   | Job'ів | Wall-clock сума | Billed (ceil/job) |
| ------------------------------------- | ------------------------- | ----------- | ------ | --------------- | ----------------- |
| #103 (A8 preflight, 2026-08-09)       | `docs/a8-preflight`       | 31307574179 | 10     | 10.8 хв         | **18 хв**         |
| #101 (z_bracket registry, 2026-08-07) | `feat/registry-z-bracket` | 31159463433 | 10     | 9.7 хв          | **16 хв**         |
| #99 (orphan artifacts, 2026-08-05)    | `docs/orphan-artifacts`   | 30996852725 | 10     | 9.4 хв          | **15 хв**         |

**Разом:** 49 billed-хвилин / 3 PR = **~16.3 хв/PR** у середньому (wall-clock середнє — 10.0 хв/PR).

**Порівняння з оцінкою в промпті** («зараз оцінне 25–40 хв»): **виміряне значення суттєво нижче** — 16.3 проти нижньої межі оцінки 25. Можливі причини розбіжності (не перевірялись окремо): (а) оцінка 25-40хв могла враховувати повільніші історичні прогони до оптимізацій кешування (`actions/setup-node` з `cache: pnpm` присутній у кожному job — перевірено в `ci.yml`); (б) оцінка могла включати ai-triage/ai-fix прогони (окремі workflow, не рахувались тут за прямою вказівкою промпту «повний CI» = `ci.yml`); (в) три вибрані PR — усі docs/registry-зміни без важких залежностей-бампів, можливо нерепрезентативні для PR з великими диффами в `apps/web`/`workers/cad`.

**Контекст для ADR-038 (Стадія 2):** GitHub Actions на **публічному** репо — необмежені хвилини на стандартних раннерах (поточний факт, `gh repo view` підтверджує `PUBLIC`). Ліміт стає релевантним лише ПІСЛЯ переходу в private (T5-1/ADR-038) — конкретне число квоти (напр. 2000 хв/міс) залежить від GitHub-плану акаунту, не перевірялося цим run'ом (поза скоупом read-only інспекції коду — це обліковий факт GitHub, не факт репозиторію).

## Розбіжності з `agy`

**Метод:** незалежний скан (Gemini, headless `agy -p`, read-only, файлова передача — вхід `docs/promts/inputs/agy-inspection-2026-08-input.md`, вихід `docs/promts/inputs/agy-inspection-2026-08-output.md`). `agy` отримав 3 конкретні перевірювані твердження з розділів A, C, D (не весь обсяг — цільова вибірка найважливіших знахідок, обрана для максимальної інформативності при обмеженому бюджеті одного виклику) і мав відповісти ТАК/НІ з цитатою, без доступу до висновків Claude.

`git status --porcelain` одразу після виклику — лише 2 нові файли (`agy-inspection-2026-08-input.md`, `agy-inspection-2026-08-output.md`), обидва в дозволеній зоні `docs/promts/inputs/`. Жодного scope-creep — рядок додано в `agy-stats.md` (Стадія 1 деліверабл, нижче).

## Підсумок — що з цього критично для Стадії 2 (ADR-039)

1. **Клас розриву «код+тест, 0 продакшн-викликів»** (розділ A) — це системна властивість, не один баг. Автономний агент без верифікації читатиме зелений тест як доказ enforcement — потрібен явний оракул («import-usage checker»), якого сьогодні немає в CI.
2. **Локальний headless-прогін (`docs/16`) не має ЖОДНОГО механічного deny** — увесь захист сьогодні живе виключно в `ai-fix.yml` (GitHub Actions), не портативний на A8 без явного перенесення.
3. **Digest-cron задекларований як завершений, механізму в git немає** — найслабша ланка serед 5 джерел сигналу; якщо A8-перехід успадкує лише те, що є в git, digest не запрацює без ручного відтворення.
4. **`agy` систематично вигадує деталі** (3/3 записи `agy-stats.md`, кожен ≥1 вигаданий факт) — кількісний аргумент для рішення про ізоляцію/верифікацію Gemini-пулу в ADR-039.
5. **Заявлена вартість CI (25-40 хв) вища за виміряну (~16.3 хв/PR)** — коригує economics-обґрунтування self-hosted раннера, варто перевимірити на більшій вибірці PR перед фіналізацією ADR-038/039 числами.
