# Відповіді на рев'ю №1 — план Ansible-ролі `a8`

## 1. Що в плані §2 зламається при першому ж застосуванні?

Зламається **Задача 2** (Довіра Claude Code).
**Причина:** У плані вказано `виклик tools/scripts/measure-trust.sh set /home/agent/hart`. Проте такого скрипта не існує. Відповідно до `docs/19_A8_PREFLIGHT.md` (рядок 561), правильний скрипт має назву `trust-worktree.sh`, а дія для додавання — `add`:

> «Що з цього зроблено. tools/scripts/trust-worktree.sh (check/add/remove, ідемпотентний) + виклик add в autorun.sh»
> Виклик з плану не спрацює і впаде з помилкою відсутності файлу або невірного аргументу.

Також, **Задача 8** (Креденшал на push). Оскільки дефолт — «не заданий», а роль містить `assert на початку з поясненням`, плейбук просто заблокує і зупинить виконання всієї ролі `a8.yml` на самому початку, доки креденшал не буде надано явно.

## 2. Чого в переліку дев'яти вимог бракує, щоб демон справді зміг працювати вночі?

Згідно з `docs/19_A8_PREFLIGHT.md` §6, Ansible-роль має автоматизувати «усе з Track B–C як код». У переліку з 9 вимог бракує наступних критичних для автономної роботи вночі речей з цих треків:

1. **Swap 8 GB** (з Track B.5). Без свопу на машині з 4 GB RAM важкі обчислення (CAD, Playwright) призведуть до OOM-killer і аварійної зупинки демона.
2. **Ліміт логів Docker** (`max-size: 10m` з Track C.2). Без цього постійний запуск контейнерів швидко вичерпає 40 GB дискового простору.
3. Відсутні базові кроки безпеки та залежностей, що згадуються в Track B-C: налаштування UFW, SSH, `unattended-upgrades`, встановлення самого Docker та Node/Playwright (інакше агенту не буде в чому працювати).

## 3. Де я видаю припущення за факт?

Ви видаєте за факт наступне твердження в §2 плану:

> «Пароля Ansible-vault на A8 немає і не буде за інваріантом docs/19 §7 п.1. Дописавши роль у site.yml, ми зробили б A8-прогін залежним від секрету, якого на машині не існує.»

**Це припущення хибне**, оскільки для розгортання через Ansible машині A8 взагалі не потрібен пароль vault. Ansible виконується і розшифровує секрети _локально_ на машині-деплой-станції, відправляючи на A8 вже розшифровані команди по SSH.
Цитата з `infra/ansible/ansible.cfg` (рядки 12-13):

> «Лінивий vault: запитує пароль один раз через --ask-vault-pass АБО з ~/.vault_pass. Реальний шлях ставимо ENV-перемінною ANSIBLE_VAULT_PASSWORD_FILE на деплой-станції.»
> Отже, розміщення ролі у `site.yml` не зробило б A8 залежною від пароля vault на ній.

## 4. Домени для allowlist'а та можливі проблеми з `-j DROP`

**Обов'язкові домени для Claude Code:**

- `api.anthropic.com` (виклик LLM)
- `github.com` та `api.github.com` (репозиторій, gh cli, створення PR)
- `registry.npmjs.org` (завантаження пакетів через `pnpm`)

**Щодо `-i docker0 -j DROP`:**
Так, це зробить контейнер непрацездатним через **блокування DNS (порт 53)**.
Фільтр `ipset` працює виключно за IP-адресами. Коли контейнеру необхідно резолвити `api.anthropic.com`, його перший запит буде спрямований до DNS-сервера. Якщо IP-адреси DNS-сервера не буде в наборі `ipset`, DNS-запит відхилиться правилом `DROP`, і контейнер не зможе розрезолвити жоден із дозволених доменів.

## 5. Assertion'и: як довести, що хук pre-commit справді спрацьовує

Перевірка наявності файлу хука не гарантує його роботи (наприклад, через відсутність бінарника `lefthook` у PATH, як доведено в `measurement-7-push.md` §4 п.6).
Щоб перевірити поведінку в `tasks/verify.yml`, можна запустити `ansible.builtin.command`:

1. Запустіть `docker run` у середовищі агента (з потрібними правами та `$PATH`).
2. Спробуйте виконати `git commit`, який містить **завідомо невалідні дані** (наприклад, файл, що порушує linting або prettier).
3. Зробіть `assert`, що команда `git commit` впала (повернула `exit code > 0`) і що в stderr/stdout наявний вивід від `lefthook`, який вказує на блокування коміту. Це буде поведінковим доказом працездатності хука.
