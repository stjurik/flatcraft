# Вхід рев'ю №1 — план Ansible-ролі `a8` (ДО написання)

**Роль для тебе:** Рев'юер. **Що оцінюєш:** план, не код — коду ще немає.
**Обмеження виклику:** не виконуй bash. Читай файли лише через `read_file`.
Пиши **виключно** у `docs/promts/inputs/agy-a8-role-1-output.md`, більше нікуди.

---

## 0. Контекст

Машина A8 (Ubuntu 24.04, kernel 6.8.0-139) має стати середовищем автономної розробки:
демон бере задачу з черги на диску, створює git-worktree, запускає сесію Claude Code у
контейнері, віддає draft PR. Зараз машина налаштована **руками**; задача — описати її
Ansible-роллю, щоб стан відтворювався з чистого клону.

Файли для читання (усі в цьому репозиторії):

- `docs/19_A8_PREFLIGHT.md` — §0.2 рішення Q1–Q13, §3 Track B, §6 «що ви НЕ ставите руками», §7 інваріанти
- `docs/03_DECISIONS.md` — ADR-039 (рядок 2150 і далі), особливо складові 2, 3, 4
- `docs/promts/inputs/measurement-6-git-in-container.md` — §4 вимоги до образу
- `docs/promts/inputs/measurement-7-push.md` — щойно доданий протокол виміру `push`
- `infra/ansible/site.yml`, `infra/ansible/ansible.cfg`, `infra/ansible/roles/base/tasks/main.yml` — наявні конвенції

## 1. Виміряні факти, на яких стоїть план

Кожен має дослівний протокол у репозиторії. Не приймай їх на віру — перевір цитатою з файлу,
і якщо моє формулювання розходиться з джерелом, це і є цінна знахідка.

1. UID контейнера мусить дорівнювати власнику примонтованого репо (`agent`, uid 1002),
   інакше git → 128 `dubious ownership`.
2. `$HOME` контейнера має існувати і бути записуваним, інакше `pnpm` падає на кеші corepack.
3. git-identity задається явно, інакше `commit` → 128.
4. `push` із контейнера **не працює: креденшала на запис немає ніде** — ні в `$HOME`, ні в
   `~agent`, ні в `credential.helper`, ні в змінних середовища.
5. Зависання `push` дає **лише** псевдотермінал (`docker run -t`). Без нього git падає за 128
   одразу; `GIT_TERMINAL_PROMPT=0` — підстраховка, не несуча конструкція.
6. Branch protection на `main` існує (PR + 1 апрув + 10 required checks), але
   **`enforce_admins: false`** — адміністратор її обходить. Rulesets порожні.
7. У ланцюзі `DOCKER-USER` stateful-RETURN стоїть **перед** DROP; лічильники DROP `0 → 0`;
   вихідний трафік контейнерів не фільтрується взагалі.
8. `agent` **справді без sudo**, але в групі `docker` (`docker:x:988:runner,agent`).
9. Хуки в контейнері — **тихий no-op**: `.git/hooks/pre-commit` виконується, `lefthook` не
   знаходиться в `PATH`, друкується попередження, **коміт усе одно проходить** (exit 0).

## 2. План ролі

**Окремий playbook `a8.yml` (`hosts: a8`), не роль у `site.yml`.** Причина: `site.yml` має
`hosts: staging`, `become: true` і `vars_files: group_vars/all.vault.yml`. Пароля Ansible-vault
на A8 немає і не буде за інваріантом `docs/19` §7 п.1. Дописавши роль у `site.yml`, ми зробили
б A8-прогін залежним від секрету, якого на машині не існує.

Структура: `infra/ansible/roles/a8/{tasks,handlers,templates,defaults,README.md}`, окремий
`tasks/verify.yml` з чистих `assert` під тегом `verify`.

Дев'ять вимог, кожна має стати задачею + assertion'ом:

| #   | Вимога                                                                                           | Як планую реалізувати                                                                              |
| --- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |

| 2   | Довіра Claude Code — один ідемпотентний запис на **корінь клону**, не на worktree                | виклик `tools/scripts/measure-trust.sh set /home/agent/hart`, `changed_when` за виводом            |

## 3. Розвилка, на яку найбільше потрібна твоя думка — egress-allowlist

`CLAUDE.md` §6.1 описує «allowlist вихідної мережі» як наявну властивість середовища. Виміряно:
його немає. Проблема реалізації в тому, що allowlist осмислений у **доменах**
(`api.anthropic.com`, `github.com`, `registry.npmjs.org`), а `iptables` оперує **адресами**, які
в CDN ротуються.

Три варіанти, які я бачу:

- **(а) `ipset` + таймер оновлення.** Роль створює `ipset hash:net`, скрипт резолвить список
  доменів і CIDR'и з `https://api.github.com/meta`, systemd-таймер оновлює кожні N хвилин.
  Правила в `DOCKER-USER`: `-i docker0 -m set --match-set a8_egress dst -j RETURN`, далі
  `-i docker0 -j DROP`. Мінус: між оновленнями можливий проміжок, коли легітимна адреса ще не
  в сеті; фільтр за адресою не розрізняє два домени на одному CDN-IP.
- **(б) HTTPS-проксі з доменним фільтром** (Squid/tinyproxy), контейнер ходить лише через
  проксі, прямий вихід DROP. Плюс: фільтр справді доменний. Мінус: міняє конструкцію
  контейнера (`HTTPS_PROXY`, довіра до CA при перехопленні), і частина інструментів проксі
  ігнорує.
- **(в) не реалізовувати зараз**, натомість виправити `CLAUDE.md` (сказати правду про стан) і
  винести allowlist окремою задачею.

Моя ★ — **(а)**, бо вона дає механічну межу сьогодні й не переписує конструкцію контейнера.

**Питання до тебе, і відповідай конкретно:**

1. Що в плані §2 зламається при першому ж застосуванні? Назви задачу і причину.
2. Чого в переліку дев'яти вимог бракує, щоб демон справді зміг працювати вночі?
3. Де я видаю припущення за факт? Перевір цитатою з названих файлів.
4. Варіант (а) для allowlist'а: які конкретні домени є обов'язковими, без яких прогін Claude
   Code у контейнері не працює? І чи не зробить `-i docker0 -j DROP` непрацездатним щось, про
   що я не подумав (DNS, NTP, оновлення сертифікатів)?
5. Assertion'и: як довести, що хук `pre-commit` **справді спрацьовує**, а не що файл існує?
   Мене цікавить перевірка поведінки, яку можна виконати в `tasks/verify.yml`.
