### 1. `pult-01-schema` — обгортка розділу і правило «застарів»

- **Після merge:** #159. **Клас:** звичайний. **Оракул:** `bash tools/scripts/dash-schema.test.sh`

```text
Зроби основу, на якій стоять усі збирачі пульта.

1. tools/dashboard/snapshot.schema.json — JSON Schema обгортки розділу з ADR-042 §2:
   schema_version (1), section, title, source, collected_at (UTC ISO 8601), interval_s (>0),
   status (ok|stale|error|not_measured), origin (measured|reading|estimate), data (object).
2. tools/scripts/dash-schema.sh — бібліотека (source) і CLI:
   - envelope <section> <title> <source> <interval_s> <origin> <status> <data.json> [--now T]
     → друкує обгортку; collected_at = --now або поточний час UTC;
   - stale <collected_at> <interval_s> [--now T] → exit 0, якщо розділ застарів:
     вік > 3 × interval_s; час у майбутньому більш ніж на interval_s — окремий вихід
     «годинник», не «свіже»;
   - validate <file> → "ok" або "reject <поле>[,<поле>…]" (exit 3), усі причини, а не перша.
     Перелік дозволених значень status і origin validate бере з snapshot.schema.json через
     jq, а не дублює в коді — одне джерело правди.
3. tools/scripts/dash-schema.test.sh — сценарії: свіже/застаріле/рівно на межі 3×;
   час у майбутньому; кожне обов'язкове поле відсутнє; невідомий status ("green");
   data не об'єкт; кілька причин одразу. Мутанти: множник 3 → 30; прийняти невідомий status;
   stale повертає «свіже»; validate зупиняється на першій причині.

Сильний оракул: якщо validate пропустить status "green" або stale не спрацює на віці
4 × interval_s — тест червоний.
```

Як перевірити очима (очікую в описі PR):

- `bash tools/scripts/dash-schema.sh envelope t5 "Трек T5" docs/02 3600 measured ok <(echo '{}')` друкує JSON з усіма дев'ятьма полями.
- `validate` на файлі з `"status": "green"` відповідає `reject status`.

### 8. `pult-02-page` — сторінка за макетом v3

- **Після merge:** задача 1. **Клас:** звичайний. **Оракул:** `bash tools/scripts/dash-page.test.sh`

```text
Зроби сторінку пульта: tools/dashboard/index.html за затвердженим макетом v3 — той самий
порядок розділів (штамп і «Квоти ШІ» → 1 Чекає на вас → 2 Черга A8 і процеси за розкладом →
3 A8 зараз → 4 Рецензенти й квоти → 5 Трек T5 → 6 Продукт і процес → 7 Джерела даних),
ті самі кольори станів, світла і темна тема, ширина телефона без горизонтальної прокрутки.

Дані сторінка бере з window.SNAPSHOT у файлі snapshot.js поруч: {collected_at, sections: [обгортки]}.
Файлу немає → сторінка каже «знімка немає — запустіть tools/scripts/dash-collect.sh», і нічого
на ній не зелене. З параметром ?example сторінка бере tools/dashboard/fixtures/snapshot.example.js
і на кожному розділі показує тег «приклад».

Логіка — окремим файлом tools/dashboard/render.js, чисті функції без DOM:
- sectionState(env, now) → ok | stale | error | not_measured | missing (правило «застарів» —
  те саме, що в dash-schema.sh: вік > 3 × interval_s);
- sourcesSummary(envs, now) → {ok, total} — «Джерел N з M» рахує лише ok;
- renderSection(env, now) → HTML-рядок; реєстр WIDGETS[section]; розділ без віджета —
  загальний вигляд «ключ — значення» з позначкою «без віджета».
Віджети хвилі 1 — лише t5 і trend (графік тижнів: продукт / процес, як у макеті). Решта
розділів до своїх хвиль показується загальним виглядом або «не підключено».

Увага: сторінку відкривають як файл (file://). ES-модулі (type="module", import) браузер
з file:// не завантажує — render.js має бути звичайним скриптом, який і створює глобальний
об'єкт для сторінки, і віддає module.exports для Node.
CI ганяє `pnpm exec eslint . --max-warnings=0`, і він перевіряє й tools/dashboard/*.js:
глобальні імена (window, document, module) оголоси коментарем /* global … */ і прожени
eslint сам перед комітом; eslint.config.mjs не міняй.

Тест: tools/dashboard/render.test.js під `node --test`, запуск — tools/scripts/dash-page.test.sh.
Сценарії: stale, error, not_measured і missing ніколи не дають зеленого класу (st-good) —
ні в розділі, ні в штампі, ні в «Джерел N з M»; невідомий розділ — загальним виглядом;
розділ зі старим collected_at, але status "ok" у файлі — все одно stale; текст з
<script> у data виводиться як текст, а не як розмітка. Мутанти: sectionState ігнорує вік;
sourcesSummary рахує stale як ok; renderSection не екранує HTML.
```


### 4. `pult-06-inbox`

- **Після merge:** задача 7 і рішення yurii про рядок `Merge після: #N` (питання 3 опитування).
- **Клас:** звичайний. **Оракул:** `bash tools/scripts/dash-inbox.test.sh`

```text
tools/scripts/dash-inbox.sh [--from DIR] [--now T] — розділ "inbox", interval_s 900,
origin measured. Без --from бере дані через gh (лише читання): відкриті PR з checks,
draft, mergeable, created_at і описом; тіло issue #78. З --from — ті самі дані з JSON-файлів
у DIR (так працюють тести; у контейнері оракула gh не автентифікований). Хто рецензував PR —
з рядків docs/promts/inputs/agy-stats.md, де згадано «PR #N».

Порядок — алгоритм ADR-042 §7, шість класів; усередині класу старіше вгорі; кожен рядок
має поле why — чому він на цьому місці:
1. розблоковує інших: PR не draft, усі checks success, є рядок рецензії в журналі, і на нього
   посилається інший PR рядком «Merge після: #N»;
2. має термін: пункт #78 з датою «до YYYY-MM-DD»;
3. решта готових до merge PR: спершу ланцюжок у його порядку, потім готові PR без рядка
   «Merge після» і без залежних — з позначкою «ланцюжок не вказано»;
4. рішення без терміну: пункти #78 з префіксом [рішення];
5. ручні кроки: пункти #78 з префіксом [ручний] або без префікса;
6. чекає не на вас: draft, checks ще йдуть або червоні, немає рецензії, чекає іншого PR.
Викреслені пункти #78 ([x]) не показуються.
Дата не у форматі «до YYYY-MM-DD» (наприклад «до 5.10», «до 05.10.2026», «до п'ятниці»)
не губиться мовчки: такий пункт іде в клас 2 з why «термін не розпізнано — перевірте
формат дати», а не в клас 4 чи 5.

Тест на фікстурах: по одному PR/пункту кожного класу, вхід у перемішаному порядку →
вихід рівно в порядку класів; ланцюжок A ← B ← C; цикл «Merge після» (A після B, B після A)
не зависає і позначається; PR з червоним check не потрапляє в класи 1 і 3; готовий PR без
ланцюжка — у класі 3, а не 6. Мутанти: переставити класи 2 і 3; draft вважати готовим;
ігнорувати «Merge після»; готовий PR без ланцюжка відправити в клас 6; пункт із датою
не в тому форматі відправити в клас 5 без позначки.
```

Як перевірити очима:

- На пульті розділ «Чекає на вас» показує PR у тому самому порядку, що й ручний перелік оркестратора в останньому звіті, і біля кожного — чому він там.
- PR з CI, що ще йде, — внизу, у «чекає не на вас».
